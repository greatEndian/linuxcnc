  MULTICHANNEL LINUXCNC  —  DESIGN FREEZE (Phase 0)
  "one motion, N channels"  —  Fanuc multi-path style
  Status:   DESIGN FROZEN 2026-06-10 — NO CODE WRITTEN YET (by decision)
  Decided:  after research of Siemens 840D (channels/BAG/WAITM/GET-RELEASE),
            Fanuc 2-path (paths/waiting-M/balance cut/composite control),
            LinuxCNC internals, and a 4-solution trade study (see notes below).
================================================================================

GOAL
----
Run N independent G-code programs ("channels") simultaneously in ONE LinuxCNC
session: independent start/stop/feed per channel, cycle-accurate synchronization
between channels, Fanuc-style coordination codes, all axes on ONE EtherCAT bus.
Primary reference machine: 2-path lathe (most common industrial case), but the
design is GENERIC — nothing machine-type-specific in the core.

THE ARCHITECTURE
----------------
  CHANNEL 1 stack (stock binaries):        CHANNEL 2 stack (stock binaries):
    GUI - halui - milltask - io              GUI - halui - milltask - io
     |  NML buffer set #1 (.nml #1)           |  NML buffer set #2 (.nml #2)
     |  own INI, own TOOL_TABLE               |  own INI, own TOOL_TABLE
     v                                        v
    cmd/status shmem area ch0                cmd/status shmem area ch1
     +--------------------+--------------------+
                          v
        ONE motmod in ONE servo thread (e.g. 250us/1kHz)
          coord_tp[0..N-1]            <- one TP per channel, ticked every cycle
          joint-ownership table       <- global joint -> owning channel (DYNAMIC-capable)
          per-channel letter->joint   <- each channel has its OWN full XYZABCUVW space
          waiting-M rendezvous engine <- TRANSPORT-AGNOSTIC (see scaling rule)
          ONE HAL - ONE lcec - ONE EtherCAT bus

KEY PRINCIPLE (decided): synchronization quality = how much clock you share.
All channels share ONE servo thread = ONE interpolation clock = inter-channel
sync is exact by construction. This is how Fanuc runs 2-path inside one CNC.

FROZEN DECISIONS
----------------
D1. Channels are GENERIC, count N (target 2, design allows more; joints<=16).
D2. Each channel = native LinuxCNC axis architecture: its own complete
    XYZABCUVW letter space. INI maps channel axes to global joints:
        [CHANNEL_1] COORDINATES=XZCY  JOINTS=0,1,2,3   SPINDLES=0
        [CHANNEL_2] COORDINATES=XZ    JOINTS=4,5       SPINDLES=1
    (illustrative syntax — finalized in phase 1)
D3. Userspace stacks (milltask/io/halui/GUI) are UNCHANGED stock binaries,
    one set per channel, isolated by per-channel .nml + SHMEM_KEY (both already
    INI-configurable). GUI choice belongs to the integrator.
D4. Waiting-M sync codes: M200-M229, Fanuc convention - the SAME M-number in
    two (or more) programs is a rendezvous point; both queues drain (M-codes
    are queue busters), both channels block until all arrive, then continue
    in the same servo cycle. Optional P-word = channel mask for N>2.
    Deadlock guard: INI timeout + GUI error naming who waits for whom.
D5. Stop semantics: hardware E-STOP and hard limits = ALWAYS machine-global
    (safety floor, not configurable). Software stop/abort/feed-hold = exported
    per channel as HAL pins (motion.N.*) PLUS global pins; the integrator
    selects propagation policy in HAL.
D6. Joint-ownership table is runtime-DYNAMIC from day 1 (axis sharing /
    Fanuc composite-style exchange is a config choice, not a redesign);
    the exchange COMMANDS themselves are phase 5.
D7. Backward compatibility golden rule: channel count defaults to 1 and the
    result must be BIT-IDENTICAL to today's behavior. Existing configs are
    the regression suite. motmod HAL pins become motion.N.* with legacy
    aliases for channel 0.
D8. SCALING RULE (the A+D merge): this design is one "timing domain".
    Machines needing radically different cycle times get N timing domains,
    each a full multichannel motion process on its own bus/NIC, bridged by
    the SAME waiting-M codes over a bridge transport (handshake-grade sync).
    Cost deferred (+2-4 wk when ever needed). Today's only obligations:
    rendezvous engine transport-agnostic; launcher must not assume exactly
    one motion process. NEVER promise cycle-accurate sync ACROSS domains.

TIMING BUDGET (frozen 2026-06-10, user decision)
------------------------------------------------
 Development and phase-1..4 validation run at SERVO_PERIOD = 1 ms (1 kHz).
 Rationale: separates functional correctness from performance tuning; EtherCAT
 CSP drives close their own loops internally, 1 kHz interpolation is sufficient
 for the reference lathe. After MC1 measurements prove headroom, the period is
 tightened stepwise toward 250 us. Never tune performance and debug
 functionality in the same step.

PER-CHANNEL TELEOP (WORLD-MODE) JOG - validated design (2026-07-10)
------------------------------------------------------------------------
PROBLEM (user-found): world/teleop jog is not channel-aware. axis.c holds
ONE machine-global axis_array[EMCMOT_MAX_AXIS]; the TELEOP path feeds ONE
global carte_pos_cmd through ONE kinematicsInverse() call whose loaded
module (trivkins coordinates=...) only describes channel 0's joints. A
secondary channel's world jog therefore drives ch0's axes/joints and its
velocity appears on ch0's DRO; the jogging channel itself never moves.
Joint-mode jog is unaffected (correctly mchan-scoped via free_tp).

DECISION (user, 2026-07-08): build the real per-channel fix, not a
refuse-with-error mitigation.

VALIDATED DESIGN (thesis + 2 evidence-driven amendments, 2026-07-10):

  Core: a per-channel axis dimension, fixed-size and letter-indexed -
      static emcmot_axis_t axis_array[EMCMOT_MAX_CHANNELS][EMCMOT_MAX_AXIS];
  kept PRIVATE inside axis.c (amendment 1: emcmot_axis_t is deliberately
  module-private; nesting it into emcmot_channel_t would break the module
  boundary and drag planner state into shmem for nothing). Channel-aware
  API entry points (axis_chan_*) take an explicit bounded channel index;
  the existing legacy API keeps its signatures and forwards to channel 0,
  so every existing call site is untouched (D7 bit-identity by
  construction, no shmem/ABI change, nothing new for the MC2b snapshot
  to tear).

  Kinematics (amendment 2): secondary-channel world jog uses the
  channel's own axis_to_joint[] map as its (identity) inverse kinematics.
  Generic per-channel kinematicsInverse() is FACTUALLY blocked today:
  (a) genserkins is ITERATIVE - it seeds from the passed-in joints[], so
  interleaved per-channel calls through an impure module produce garbage
  by construction; (b) the loaded module's coordinates= string describes
  exactly one letter->slot mapping and the kins API has no channel
  parameter. Non-identity kins on a secondary channel is refused with a
  clear operator error until the kins API grows a channel dimension
  (upstream conversation). For identity kins the axis_to_joint remap IS
  kinematicsInverse's result, computed without the redundant call.

  Existing scaffolding reused: MC24 per-channel envelope = the limits
  source (already stored + configured per channel); virt_state (already
  virtualized - a secondary channel's teleop enable never touches the
  global motion state); mchan_run_secondary() = the executor that drives
  the channel's teleop planners each cycle.

RISK REGISTER (ranked; each is an implementation checklist item):
  1. Jog-abort friendly fire: axis_jog_abort_all() has ~10 GLOBAL call
     sites (ABORT, COORD entry, jog-stop pin, teleop transitions). Every
     site must be audited: machine-global events abort ALL channels'
     jogs; channel-scoped events abort only that channel's.
  2. Velocity/position DRO regression: the mchan_channel_free_vel()
     helper (12b3c041a1) reads free_tp only - the channel's teleop
     planner velocity must be included or the world-jog velocity DRO
     reads 0 again. Same for the per-channel stat position overlay.
  3. Homing gate: per-channel teleop requires THAT CHANNEL's joints
     homed (not allhomed); define explicitly.
  4. Busy refusal: world jog refused while the channel's coord_tp runs.
  5. Envelope-unset trap: MC24 limits are zero-until-configured; a zero
     envelope must produce a LOUD refusal, not a silent no-move (the
     free_tp.max_acc lesson).
  6. HAL pins: axis.<letter>.* stays channel 0 (legacy compat).
     Per-channel axis pins + per-channel jogwheels are DEFERRED -
     GUI/keyboard jog arrives via NML, needing no new pins.
  7. External offsets remain channel-0-only (threaded through COORD
     bound updates); splitting them is a separate future effort.

VALIDATION GATES for the implementation:
  - Equivalence: on ch0/trivkins the axis_to_joint remap must produce
    joints bit-identical to the kinematicsInverse() path.
  - New matrix rows: ch1 world jog moves ONLY joints 4-7 with position
    AND velocity on ch1's DRO only; mirror for ch0; refusal while the

TRADE STUDY (why this architecture; summary)
--------------------------------------------
 A. N full LinuxCNC instances : independence king, but two interpolation clocks
    -> drift/jitter, sync via bridges only, HAL keys hardcoded (patch needed),
    one IgH master per process -> 2nd NIC. WRONG tool when sync is the goal.
    Survives as the deferred cross-domain layer (D8).
 B. Full native re-architecture incl. UI: the real 840D, person-months,
    UI rewrite — UI is integrator's domain here, so B's edge is moot.
 C. 9-axis merge (one TP, ch2=UVW): perfect sync but NO independent start/stop,
    no per-channel letter space, no arcs for ch2. Rejected by requirements.
 D. SELECTED: one motion process with N TPs + N stock userspace stacks.
    Cycle-accurate sync, independent channels, one EtherCAT bus, Fanuc
    ergonomics (each path programs its own X/Z...), ~1/3 the cost of B.
